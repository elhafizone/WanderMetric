# Offer guides — one indexable guide page per partner offer

Status: draft for owner review · 2026-10-04

## Purpose

Today the site has editorial pages and a handful of partner buttons. The owner's
model is different: each affiliate programme (Klook, KKday, Tiqets…) lists many
individual offers. Every offer should become a **comprehensive, original guide
page** that answers what a visitor needs before booking, ends in a clearly
disclosed affiliate link, and can rank on its own for that offer's search terms.

Success: ~10 published guides per activity/transfer programme in phase A, each
factually sourced, none templated-looking, each with a working `/go/{slug}` link.

## Owner decisions (2026-10-04)

1. Start with 10 offers per programme.
2. Facts only. Nothing invented.
3. No copied text; every sentence is written fresh.
4. No prices. A range may be shown only if the offer page states it, labelled with
   the date it was read.
5. Fix the technical blockers.
6. Existing `/affiliate-disclosure` page stays; one short disclosure line sits next
   to every booking button.
7. Offers are read in the browser like any visitor; links are generated by the
   owner's Travelpayouts dashboard. No API, no bulk scraping.

## Current state (verified against the live database, 2026-10-04)

- 29 programmes, 33 links, 1 provider (`travelpayouts`), 8 activities, 13 cities.
- `activities` has `kind` (`activity|tour`), `city_id NOT NULL`, `summary`, `body`,
  `duration_minutes`, `status`, and **no publish gate** (only guides have one).
- `affiliate_links` holds the destination; `affiliate_link_placements` links a link
  to a content row; `resolve_affiliate_link` returns the stored destination and an
  optional `deep_link_template`.
- `/go/[slug]` returns 404 until `SUPABASE_SERVICE_ROLE_KEY` is in the environment.
- The Supabase MCP now sees the WanderMetric project (`vxhmtqhnjlkrdjruexmv`).

## Scope

**Phase A (this spec):** activity, tour and transfer programmes — `klook`, `kkday`,
`tiqets`, `go-city`, `wegotrip`, `welcome-pickups`, `kiwitaxi`, `gettransfer`,
`intui-travel`. Target ≈ 90 guides, delivered as a 3-offer pilot first.

**Out of scope:** eSIM-per-country and car-hire-per-city (phase B, different
template), claims programmes (AirHelp, Compensair), hotel and flight pages,
conversion ingestion, image sourcing.

## Design

### 1. Source of truth: one JSON file per offer

`content/offers/<programme>/<slug>.json`, reviewed in git before anything is
published.

```
programme        e.g. "klook"
city             slug of an existing city (new cities need a separate decision)
kind             "activity" | "tour"
title, slug
source_url       the offer page the facts were read from (provenance only)
read_on          date the page was read
facts            only what the page states: duration, languages, inclusions,
                 exclusions, meeting point, group size, cancellation wording,
                 itinerary stops. Absent fact = absent key.
price_note       optional, e.g. "Listed from about X to Y (read 2026-10-05)"
affiliate_url    the tpx.li link generated in the owner's dashboard
summary, body    original guide text (markdown)
```

Missing facts are never filled in. If the offer page is too thin to support a
useful guide, the offer is skipped and replaced.

### 2. Database (one migration)

- `activities.program_id` (FK `affiliate_programs`), `source_url text`,
  `facts jsonb not null default '{}'`, `price_note text`.
- Publish gate trigger/CHECK on `activities`, enforced by the database
  (rule 3 and 8): to be `published`, body ≥ 800 characters, `facts` non-empty,
  `source_url` present, and an active link in `affiliate_link_placements`.
- No numeric price column. `price_note` is free text by design.
- RLS unchanged: drafts stay invisible to anon.

### 3. Affiliate link handling

- Store each generated `tpx.li` URL in `affiliate_links.destination_url`
  (`deep_link_template` null) and place it on the activity through
  `affiliate_link_placements`. The URL never appears in JSX.
- **To verify first:** that the provider adapter returns a stored `tpx.li`
  destination unchanged rather than re-wrapping it. If it re-wraps, the manual
  link bypass is added to the adapter (one file) with a test.

### 4. Page template

Sections appear only when a fact supports them, and their order and emphasis vary
with the offer (a temple day-trip leads with logistics and timing; a museum pass
leads with what the pass covers):

At a glance (facts) · who it suits · what to expect · practical tips · before you
book · FAQ drawn only from facts · booking button with one disclosure line beside
it (`rel="sponsored nofollow"`).

Structured data: breadcrumbs and FAQ only where facts exist. No rating, no price
markup.

### 5. Discovery and linking

Hub pages by city × programme and programme × cities; related offers linked from
each guide; all included in the existing database-driven sitemap.

### 6. Workflow per programme

1. Browse the programme site; choose 10 varied offers (different cities and
   types; skip duplicates and thin pages).
2. Read each offer's facts.
3. Paste the offer URL into the Travelpayouts dashboard; copy the generated link.
4. Write the JSON file with original text.
5. Import the batch as **drafts**.
6. Owner reviews; approved drafts are published.

Pausing for the owner on a login expiry or a CAPTCHA; neither is bypassed.

### 7. Import

A local, server-only script upserts the JSON files into the database with the
service-role key from `.env.local`. All CHECK constraints and triggers still
apply. Imports are idempotent on `(city, slug)` and create drafts only.

### 8. Images

No images copied from partner sites. Guides use existing licensed city imagery or
none. Sourcing is a later task.

## Risks

- **Thin source pages** → fewer than 10 usable offers for a programme. Mitigation:
  skip and report; never pad.
- **Search quality**: 90 guides from one template can look mass-generated.
  Mitigation: facts-driven section selection, the 800-character floor, and a
  pilot reviewed before scaling.
- **Stale facts**: `read_on` is stored and shown; guides are re-checked on a
  schedule decided after the pilot.
- **Programme terms**: reading pages like a visitor and writing original text keeps
  within normal use; if a programme's terms say otherwise, that programme is
  dropped.

## Testing

- Migration: gate rejects a publish missing any required field (SQL tests via the
  Supabase MCP on a branch or the live DB with rollback-safe fixtures).
- Core: unit tests for the section selector and facts → page model (framework-free
  in `src/core/`).
- Importer: dry-run mode that validates every JSON file against the same rules and
  prints what would change.
- `npm run verify` stays green.
